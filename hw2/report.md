# 1. Проект и стек (hw_ai_rules.md)

## Проект

HealthyBox — мобильное веб-приложение для заказа готовых наборов здорового питания на день или неделю. MVP: каталог рационов, детальное меню по дням, корзина с датой первой доставки, затем backend и CI/CD. Проект общий для ДЗ 2–6.

## Технологический стек

| Слой | Технология |
|---|---|
| Язык | TypeScript (strict) |
| UI | React 18, обычный CSS с переменными, mobile-first |
| Сборка | Vite |
| Тесты | Vitest, Testing Library, jsdom |
| Backend | Supabase (PostgreSQL, Auth, RLS) |
| CI/CD | GitHub Actions, Vercel |
| AI-агент | Claude Code, файл правил `CLAUDE.md` |

## Ключевые требования к коду и архитектуре

| Область | Требование |
|---|---|
| Стиль | PascalCase для компонентов и типов, camelCase для функций, отступ 2 пробела, строка до 100 символов |
| Архитектура | Экраны в pages, компоненты в components, чистая бизнес-логика в lib, данные и API в data |
| Деньги | Целые рубли, без дробных значений |
| Строгость | Запрещены any, @ts-ignore, мутация входных аргументов |
| Тесты | Для каждой функции из lib есть тест: нормальный случай, граничный случай, ошибка |
| Безопасность | Секреты только в .env, в репозиторий попадает .env.example |


# 2. Файл правил (rules.md, для Claude Code)

## 1. Роль

1. Ты — Senior Frontend-разработчик на React + TypeScript, работающий над мобильным веб-приложением HealthyBox (заказ готовых наборов здорового питания). Отвечай на русском, код и идентификаторы — на английском.

## 2. Контекст проекта

2. Стек: React 18, TypeScript (strict), Vite, Vitest + Testing Library, обычный CSS с CSS-переменными. Backend — Supabase (PostgreSQL, Auth, RLS).
3. Архитектура: `src/pages` (экраны), `src/components` (переиспользуемые компоненты), `src/lib` (чистые функции без React), `src/data` (mock-данные и API-слой), `src/hooks`. Бизнес-логика (цены, корзина, даты) живёт только в `src/lib`.
4. Деньги хранятся в целых рублях (`number`, integer). Даты — объекты `Date` без времени; в API — строки ISO `YYYY-MM-DD`.

## 3. Стиль кода

5. Именование: компоненты и типы — `PascalCase`, функции и переменные — `camelCase`, константы — `UPPER_SNAKE_CASE`, файлы компонентов — `PascalCase.tsx`, остальные — `camelCase.ts`.
6. Форматирование: отступ 2 пробела, одинарные кавычки, точка с запятой, максимум 100 символов в строке.
7. Комментарии: JSDoc только для экспортируемых функций (что делает, параметры, ошибки). Не комментируй очевидное.

## 4. Ограничения (строгие запреты)

8. ЗАПРЕЩЕНО использовать `any`, `@ts-ignore` и `as unknown as`. Вместо `any` — конкретный тип или `unknown` с проверкой.
9. ЗАПРЕЩЕНО писать компоненты-классы и использовать устаревшие библиотеки (`moment`, `enzyme`, `create-react-app`). Для дат — нативный `Date`/`Intl`.
10. ЗАПРЕЩЕНО хранить секреты и ключи в коде; только `import.meta.env.VITE_*` и `.env.example` без значений.
11. ЗАПРЕЩЕНО мутировать входные аргументы функций; возвращай новые объекты.

## 5. Формат вывода

12. Сначала список создаваемых/изменяемых файлов, затем код каждого файла отдельным блоком с путём в заголовке.
13. Каждая новая функция из `src/lib` сопровождается тестом `*.test.ts` рядом с файлом (минимум: нормальный случай, граничный случай, ошибка).
14. В конце ответа — короткий раздел «Допущения»: что было неясно и как это решено.

# 4. Chain-of-Thought (prompt_methodology.md)

## Задача

Реализовать в HealthyBox корзину с выбором даты первой доставки: набор добавляется через календарь (даты ближе чем через 2 дня недоступны), в корзине можно менять количество, при 0 позиция удаляется, итог пересчитывается.

Задача сложная: в ней сочетаются бизнес-правила, состояние, несколько экранов и тесты. Поэтому она решалась по шагам: каждый шаг опирается на результат предыдущего и проверяется отдельно.

## Шаг 1. Модель данных и чистая логика

Промпт:

```
Role: Senior Frontend на React + TypeScript (правила в CLAUDE.md).
Task: создай типы Plan, Dish, CartItem и функции calcSetPrice, addToCart, changeQty, cartTotal.
Context: деньги в целых рублях; неделя = 7 дней со скидкой 10%; дата доставки не ранее чем через 2 дня; при количестве 0 позиция удаляется; сегодняшняя дата передаётся параметром.
Format: файлы src/types.ts, src/lib/pricing.ts, src/lib/cart.ts и тесты рядом.
```

Результат: созданы типы и две библиотеки, 11 тестов (5 на цены, 6 на корзину). Все прошли с первого запуска.

## Шаг 2. Данные и компоненты

Промпт:

```
Role: Senior Frontend на React + TypeScript.
Task: создай mock-данные (3 рациона, 7 дней по 4 приёма пищи) и компоненты PeriodToggle, PlanCard, DatePickerModal, StateViews.
Context: используй функции из шага 1; состояния loading, error, empty; календарь показывает 14 дней, первые 2 недоступны; кнопки не меньше 44 px.
Format: список файлов и код с путями.
```

Результат: компоненты и данные созданы, `tsc --noEmit` без ошибок.

## Шаг 3. Экраны и сборка потока

Промпт:

```
Role: Senior Frontend на React + TypeScript.
Task: собери экраны CatalogPage, SetPage, CartPage и App с переходами каталог → набор → корзина.
Context: корзина хранится в состоянии App; срок (день/неделя) сохраняется из каталога при открытии набора; в SetPage календарь открывается по кнопке «Добавить в корзину».
Format: список файлов и код с путями.
```

Результат: работающий поток. Добавлен CSS (mobile-first, точки перелома 640 и 960 px).

## Шаг 4. Тесты потока и состояний

Промпт:

```
Role: инженер по тестированию (Vitest + Testing Library).
Task: напиши тесты состояний каталога (loading, success, error с повтором, empty), календаря и сквозной поток добавления в корзину.
Context: загрузку данных передавай в CatalogPage параметром load, чтобы подменять её в тестах.
Format: файлы *.test.tsx рядом с исходниками.
```

Результат: суммарно 18 тестов, все проходят с первого запуска.

## Шаг 5. Проверка

Промпт:

```
Role: инженер по качеству.
Task: запусти typecheck, тесты, сборку и npm audit, составь список проблем.
Format: вывод команд и список находок.
```

Результат: typecheck, тесты и сборка проходят. `npm audit` нашёл 6 уязвимостей в dev-зависимостях (подробнее в ДЗ 6).

## Что оказалось полезным

- Разделение на шаги дало проверяемые промежуточные результаты: после каждого шага запускались `tsc` и тесты.
- Передача сегодняшней даты параметром сделала логику даты детерминированной и тестируемой.
- Правила из `CLAUDE.md` не нужно было повторять в каждом промпте.

## Сложности

На шагах 1–4 ошибок не возникло. Это нужно учитывать: задача хорошо описана и мала, поэтому цепочка отработала без исправлений. Реальные исправления понадобились позже, при обновлении зависимостей (ДЗ 6).


# 5. Тестирование правил (testing.md)

## Методика

Одна и та же задача была дана агенту дважды, в двух независимых запусках:

1. Без файла правил (запуск А).
2. С файлом правил `rules.md`, вставленным в начало запроса (запуск Б).

Запуски выполнены субагентами Claude без доступа к файлам проекта, чтобы результат зависел только от текста запроса. Это не Cursor и не отдельная сессия Claude Code с автоматической загрузкой `CLAUDE.md`; правила переданы в тексте запроса.

Задача: «Нужна функция расчёта цены набора. Вход: период (day или week), цена одного дня в рублях, количество наборов. Неделя = 7 дней со скидкой 10%. Верни итоговую цену и строку для показа в UI. Напиши код и тесты».

Полные ответы без правок сохранены в файлах `raw_before_rules.md` и `raw_after_rules.md` и приведены ниже.

## Ответ агента ДО применения правил

Ключевые фрагменты (полный текст — в `raw_before_rules.md`):

```ts
export type Period = 'day' | 'week';
export const DAYS_IN_WEEK = 7;
export const WEEK_DISCOUNT = 0.10;

export function calculateBoxPrice(
  period: Period,
  dayPrice: number,
  quantity: number,
): PriceResult {
  // ...проверки...
  const dayKopecks = Math.round(dayPrice * 100);
  const days = period === 'week' ? DAYS_IN_WEEK : 1;
  let kopecks = dayKopecks * days * quantity;
  if (period === 'week') {
    kopecks = Math.round((kopecks * 90) / 100);
  }
  const total = kopecks / 100;
  // ...
}
```

И в тестах:

```ts
expect(() => calculateBoxPrice('month' as any, 500, 1)).toThrow(RangeError);
```

## Ответ агента ПОСЛЕ применения правил

Ключевые фрагменты (полный текст — в `raw_after_rules.md`):

```ts
/**
 * Считает итоговую цену набора и строку для показа в UI.
 * ...
 * @throws {RangeError} если dayPrice или quantity не положительные целые,
 * либо period не 'day' и не 'week'
 */
export function calcBoxPrice({ period, dayPrice, quantity }: BoxPriceInput): BoxPrice {
  assertPositiveInteger(dayPrice, 'dayPrice');
  assertPositiveInteger(quantity, 'quantity');
  // ...
  unitPrice = Math.floor((dayPrice * DAYS_IN_WEEK * fullPercent + 50) / 100);
  // ...
}
```

Ответ начинался со списка файлов (`src/lib/calcBoxPrice.ts`, `src/lib/calcBoxPrice.test.ts`) и заканчивался разделом «Допущения».

## Сравнение по правилам

| Правило | До | После |
|---|---|---|
| 8. Нет `any` | Нарушено: `'month' as any` в тесте | Выполнено: `any` нет |
| 8. Нет `@ts-ignore` | Не применялось | Формально выполнено, но тест использует `@ts-expect-error` (см. ниже) |
| 12. Список файлов, код с путями | Нет списка файлов, путь указан только в комментарии первой строки | Выполнено: список файлов и пути |
| 13. Тесты: нормальный, граничный, ошибочный случаи | Есть: нормальные случаи, округление до копеек, невалидный ввод; нет теста на минимальные значения | Выполнено: добавлены минимальные значения и округление half up |
| 14. Раздел «Допущения» | Есть короткий список «Замечания» | Выполнено: названный раздел с 7 пунктами |
| 4. Деньги в целых рублях | Нарушено: расчёт в копейках, допускаются дробные цены, `total` может быть дробным | Выполнено: цена и итог — целые рубли, дробная цена вызывает `RangeError` |
| 7. JSDoc на экспортируемых функциях | Нет JSDoc у функции | Выполнено: JSDoc с параметрами и `@throws` |
| 5. Именование | `calculateBoxPrice`, `WEEK_DISCOUNT` | `calcBoxPrice`, `WEEK_DISCOUNT_PERCENT`; оба варианта допустимы |
| 6. Строка до 100 символов | Выполнено | Нарушено: в нескольких строках кода и тестов длина больше 100 символов |
| 1. Роль Senior Frontend | Ответ общий | Структура ответа соответствует роли |

## Что осталось несовершенным

- **Лазейка в правиле 8.** Правило запрещает `@ts-ignore`, а агент применил `@ts-expect-error` и прямо объяснил, что это не запрещено. Правило нужно уточнить: «запрещены `@ts-ignore`, `@ts-expect-error` и `@ts-nocheck`». В исходном файле правил это не исправлялось, чтобы протестированная версия соответствовала сохранённым результатам.
- **Длина строк.** Правило 6 нарушено в варианте «после». Это показывает, что правила форматирования надёжнее поручить линтеру (Prettier, ESLint), а не только тексту.
- **Выборка.** Сравнивались по одному ответу на каждый вариант. Генерация вероятностна, поэтому выводы о том, что именно изменили правила, нужно считать предварительными.

## Краткий вывод
