# 1. Проектирование базы данных

## Сущности

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `dishes` | Блюда | `id`, `name`, `grams`, `kcal`, `protein`, `fat`, `carbs`, `ingredients[]`, `allergens[]` |
| `plans` | Рационы (типы питания) | `id`, `name`, `goal`, `kcal_per_day`, `day_price` (целые рубли) |
| `plan_meals` | Меню рациона по дням | `plan_id`, `day` (1–7), `meal_title`, `dish_id` |
| `orders` | Заказы пользователей | `id`, `user_id` → `auth.users`, `status`, `delivery_date`, `created_at` |
| `order_items` | Позиции заказа | `id`, `order_id`, `plan_id`, `period`, `qty`, `unit_price` |

## Связи

```
auth.users 1 ──< orders 1 ──< order_items >── 1 plans 1 ──< plan_meals >── 1 dishes
```

- Пользователь имеет много заказов; заказ — много позиций.
- Позиция ссылается на рацион. Меню рациона — связь «многие ко многим» между рационами и блюдами через `plan_meals`.
- При удалении пользователя его заказы удаляются каскадно, при удалении заказа — его позиции.

## Как использован AI

Требования к данным взяты из ДЗ 3 (история 10 «корзина», истории 7–9 «набор и блюдо») и переданы агенту. Схема сгенерирована агентом за один проход. При проектировании приняты три решения (итераций исправления не было, потому что SQL не запускался):

1. Правило «дата доставки не ранее сегодня + 2 дня» реализовано триггером `check_delivery_date`, а не `CHECK`-ограничением с `current_date`: ограничение зависит от времени, и при восстановлении дампа старые строки нарушили бы его. Триггер срабатывает только при вставке.
2. Цена позиции `unit_price` не должна приходить от клиента, иначе пользователь может подменить цену. Добавлен триггер `set_unit_price`, который считает цену из `plans.day_price` (неделя = 7 дней со скидкой 10%, округление до рубля, та же формула, что и во фронтенде).
3. Для итога заказа добавлено представление `orders_with_total` с `security_invoker = true`, чтобы RLS применялся от имени вызывающего пользователя.

# 4. Безопасность

## Row Level Security

| Таблица | Операция | Кто | Условие |
|---|---|---|---|
| `dishes`, `plans`, `plan_meals` | SELECT | anon, authenticated | Всегда (каталог публичный) |
| `dishes`, `plans`, `plan_meals` | INSERT/UPDATE/DELETE | никто из клиентов | Политик нет, запись только через `service_role` |
| `orders` | SELECT | authenticated | `user_id = auth.uid()` |
| `orders` | INSERT | authenticated | `user_id = auth.uid()` |
| `orders` | UPDATE | authenticated | Владелец, и после изменения владелец тот же |
| `orders` | DELETE | authenticated | Владелец и `status = 'draft'` |
| `order_items` | SELECT | authenticated | Заказ принадлежит пользователю |
| `order_items` | INSERT/UPDATE/DELETE | authenticated | Заказ принадлежит пользователю и в статусе `draft` |

Анонимный пользователь не видит и не создаёт заказы. Один пользователь не видит заказы другого.

## Аутентификация

Supabase Auth, вход по email и паролю (`signUp`, `signInWithPassword`), OAuth Google (`signInWithGoogle`, см. ДЗ 6). Функции реализованы в `src/data/supabaseApi.ts` и `src/data/accountApi.ts`; интерфейс входа и регистрации — `src/pages/AuthPage.tsx`, состояние сессии и роли — `src/hooks/useAuth.tsx`. Если в проекте включено подтверждение почты, после регистрации нужно подтвердить email.

## CORS и секреты

- REST API Supabase принимает запросы с любых источников (по документации Supabase, это стоит проверить в вашем проекте). Защита данных обеспечивается JWT и RLS, а не списком источников. Для Auth необходимо указать **Site URL** и **Redirect URLs** (адрес продакшена и `http://localhost:5173`).
- В браузер попадает только публичный `anon`-ключ. Ключ `service_role` обходит RLS и **никогда** не добавляется во фронтенд и репозиторий.
- Переменные окружения: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` в `hw4/healthybox-app/.env`; образец — `.env.example`. В репозиторий намеренно закоммитирован `.env` тестового проекта: в нём только URL и публичный ключ, секретного ключа нет.
- Проверка по коду: в `src/` нет упоминаний `service_role`.

## Роли: пользователь и администратор

Роль хранится в таблице `profiles` (`role` = `user` или `admin`). Профиль создаётся триггером при регистрации, роль по умолчанию `user`. Миграция: `supabase/migrations/0004_roles.sql`.

| Возможность | Гость | Пользователь | Администратор |
|---|---|---|---|
| Каталог и корзина | да | да | да |
| Профиль: имя, телефон, адрес доставки | нет | да (свой) | да (свой) |
| Оформление заказа, «Мои заказы» с детализацией | нет | да (свои) | да |
| Отмена оформленного заказа | нет | да (свой) | да |
| Выгрузка заказов в CSV | нет | свои | все |
| Все заказы и смена их статуса | нет | нет | да |
| Фильтры, поиск, сводка и популярность рационов | нет | нет | да |
| Вкладка «Свод»: графики, статусы, рационы, клиенты, сводный лист (сортировка, фильтр, CSV) | нет | нет | да |
| Список пользователей, смена ролей, выгрузка в CSV | нет | нет | да |
| Изменение цен рационов | нет | нет | да |

- Защита на уровне БД: функция `is_admin()` (`security definer`) и RLS-политики с ней. Клиент не может менять роль у себя: право `UPDATE` на `profiles.role` ограничено политикой «только администратор».
- Интерфейс скрывает недоступные экраны функцией `canAccess` (`src/lib/roles.ts`), но это только удобство: настоящая проверка выполняется в базе.
- Первый администратор назначается вручную в SQL Editor: `update public.profiles set role = 'admin' where email = '<почта>';`.
- Статус заказа защищён триггером `guard_order_update` (миграция 0005): без него владелец мог бы вернуть оформленный заказ в черновик и удалить его. Администратор триггером не ограничен.
- Профиль: пользователь обновляет только свою строку и только `full_name`, `phone`, `address` (миграция 0006). Так как право на колонку `role` выдано ради администратора, смену роли не-админом блокирует триггер `guard_profile_update`.
- Адрес доставки копируется в заказ при оформлении (`orders.delivery_address`, миграции 0007–0008): смена адреса в профиле не меняет прошлые заказы.
- Администратор не может изменить собственную роль в интерфейсе (защита от потери последнего администратора).

# 5. API

Используется автоматический REST API Supabase (PostgREST). Базовый адрес: `https://<project>.supabase.co/rest/v1`. Обязательные заголовки: `apikey: <anon key>`, для защищённых запросов `Authorization: Bearer <JWT пользователя>`.

| Операция | Метод и путь | Доступ | Клиентская функция |
|---|---|---|---|
| Read: каталог с меню | `GET /plans?select=*,plan_meals(day,meal_title,dishes(*))` | Публичный | `fetchPlansRemote` |
| Create: заказ | `POST /orders` | Вошедший пользователь | `createOrder` |
| Create: позиции | `POST /order_items` | Владелец черновика | `createOrder` |
| Read: заказы с итогом | `GET /orders_with_total` | Владелец | не подключено к UI |
| Update: подтверждение | `PATCH /orders?id=eq.<id>` | Владелец | `placeOrder` |
| Delete: черновик | `DELETE /orders?id=eq.<id>` | Владелец, только `draft` | `deleteDraftOrder` |
| Регистрация | `POST /auth/v1/signup` | Публичный | `signUp` |
| Вход | `POST /auth/v1/token?grant_type=password` | Публичный | `signIn` |

## Примеры запросов

Каталог:

```bash
curl "https://<project>.supabase.co/rest/v1/plans?select=id,name,day_price&order=day_price" \
  -H "apikey: <anon key>"
```

Создание заказа (дата не ранее чем через 2 дня):

```bash
curl -X POST "https://<project>.supabase.co/rest/v1/orders" \
  -H "apikey: <anon key>" \
  -H "Authorization: Bearer <JWT пользователя>" \
  -H "Content-Type: application/json" \
  -H "Prefer: return=representation" \
  -d '{"delivery_date": "2026-10-20"}'
```

Добавление позиции (цену клиент не передаёт):

```bash
curl -X POST "https://<project>.supabase.co/rest/v1/order_items" \
  -H "apikey: <anon key>" \
  -H "Authorization: Bearer <JWT пользователя>" \
  -H "Content-Type: application/json" \
  -d '{"order_id": "<id заказа>", "plan_id": "balance", "period": "week", "qty": 1}'
```

Подтверждение заказа:

```bash
curl -X PATCH "https://<project>.supabase.co/rest/v1/orders?id=eq.<id заказа>" \
  -H "apikey: <anon key>" \
  -H "Authorization: Bearer <JWT пользователя>" \
  -H "Content-Type: application/json" \
  -d '{"status": "placed"}'
```

Ожидаемые результаты для рациона «Баланс» на неделю: `unit_price = 4095`.

# 7. Обработка ошибок и логирование

## Сопоставление ошибок

Функция `toApiError` переводит ошибки Supabase в сообщения для пользователя и не раскрывает технические детали.

| Условие | Код / статус | Сообщение пользователю | Что показывает UI |
|---|---|---|---|
| Нет входа | HTTP 401, `PGRST301` | Войдите в аккаунт, чтобы продолжить | Предложение войти |
| Нет прав (RLS) | HTTP 403, `42501` | Нет доступа к этим данным | Сообщение, возврат на каталог |
| Дата доставки слишком ранняя | `22023` (триггер) | Дата доставки не ранее чем через 2 дня | Сообщение в календаре |
| Нарушение `CHECK` (например, `qty` вне 1–10) | `23514` | Проверьте корректность введённых данных | Сообщение у поля |
| Прочее, сеть | 5xx | Не удалось выполнить запрос. Попробуйте ещё раз | Кнопка «Повторить» |

Для ошибки загрузки каталога уже реализовано состояние с кнопкой «Повторить» (ДЗ 4).

## Логирование

- Клиент: JSON-записи `{ts, level, msg, ...}` через `logger`; поля `email`, `password`, `token` и подобные заменяются на `[REDACTED]`.
- Сервер: логи Supabase Dashboard → Logs (API, Postgres, Auth). Self-hosted логи не настраивались.

# 10. Процесс разработки с AI

- Схема БД, RLS-политики и клиентский слой сгенерированы агентом по требованиям из ДЗ 3 и правилам проекта (`CLAUDE.md`).
- Принятые проектные решения (раздел 1): триггер вместо `CHECK` с датой, серверный расчёт цены, представление с `security_invoker`.
- Проверка кода выполнена `tsc` и тестами. Проверка SQL невозможна без PostgreSQL, поэтому подготовлен чек-лист.

# 11. Выводы и рекомендации

1. Supabase подходит для MVP: API и аутентификацию не нужно писать самостоятельно, а правила доступа описываются декларативно в RLS.
2. Главные риски, которые закрывает дизайн: подмена цены клиентом и доступ к чужим заказам. Их нужно подтвердить тестами на реальной БД (проверки 5 и 7).
3. Для ДЗ можно считать сданной подготовленную часть. До полной сдачи нужно развернуть проект, пройти чек-лист и добавить в приложение экран входа и оформления заказа.
4. Для продакшена дополнительно: подтверждение email, ограничение частоты запросов, резервные копии, журнал изменений заказов.
